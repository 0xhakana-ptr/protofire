# Per-crate source lines and test counts: the census
# `scripts/check-crate-tests.sh` ratchets.
#
# Each row is `<crate> <source lines> <tests run>`.  The test count is what
# `cargo test -p <crate>` reports, which is the only number that means anything:
# a `#[cfg(test)]` module in a crate that does not compile for the host reports
# zero, and that is the state this census first found two crates in.
#
# A crate with no tests fails when it is large enough to be worth one, and a
# crate that loses tests fails outright.  The number may rise freely; a fall is a
# change to this file, which is a sentence a reader can disagree with.
#
# Recording is `sh scripts/check-crate-tests.sh --record`.  A row whose crate
# has left the workspace is refused, so the file describes the tree.
#
# ## Rows that name a module
#
# A row whose first field holds `::` names one module inside a crate instead of
# the crate itself, and its line count is a dash because the source is the
# crate's: counting it here would make the crate's number depend on how its
# files happen to be split.
#
# These exist because a crate with several implementations reports one total,
# and one total cannot say whether each of them is tested.  `fs` holds PyroFS,
# tmpfs and ISO 9660; a fifth that size arriving with two hundred tests and a
# sixth with none would leave the total rising while half of what the crate
# claims went unproven.
#
# A module is watched when its row is added here, and never by `--record`: that
# is what keeps this a list of decisions rather than a mirror of the tree's
# internal structure.  A module that loses tests fails even when its crate's
# total does not fall.
